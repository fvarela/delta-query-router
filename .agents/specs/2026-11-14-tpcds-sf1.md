# TPC-DS SF1: generate, write as Delta, register in `dqr.sf1`

Status: approved

## Goal
The dev tool gets a way to load TPC-DS scale factor 1 into the project: generate the 24 tables with DuckDB on the
author's machine, write each one once as an external Delta table under our `tpcds` container, and register it in
Unity Catalog as `dqr.sf1.<table>`. Both engines then read the same files (milestone 1 onwards).

## Non-goals
- SF10 and SF100: later work (DESIGN §12 keeps "where to generate SF10" open). The functions take the schema name, but the menu only offers SF1.
- The 99 TPC-DS queries and running them on any engine (milestone 2).
- Grants to anyone else, including the future Databricks service principal (milestone 1).
- Partitioning, updates, deletion vectors (DESIGN §5: unpartitioned, written once).
- Deleting or overwriting Delta files; creating, starting, stopping or changing SQL warehouses.
- Any Azure resource change other than the one role assignment of E14, and any change to the five Unity Catalog objects of the closed spec `unity-catalog-setup`.

- Already in place (verified on `main`): the dev tool `uv run dqr`; `src/dqr/data/unity_catalog.py` (`MARKER`, `Settings`, `load_settings`, `Step`, `setup`, `teardown`); `src/dqr/cli/main.py` (`run(choose, ask, console, make_client)`, errors shown as one message through `EXPECTED_ERRORS`); `tests/test_infra.py` (`ENV_VARIABLES`, `IDENTIFYING_VARIABLES`). Catalog `dqr`, schemas `sf1`, `sf10` and external location `dqr-tpcds` on `abfss://tpcds@<DQR_STORAGE_ACCOUNT>.dfs.core.windows.net/` exist for real since 2026-11-14. Teardown drops schemas with `force=True`, which drops table metadata only, never the files; it needs no change for tables.
- Writing from the author's machine: the Bicep parameter `dataWriterPrincipalId` gives the author's user Storage Blob Data Contributor on the container (inferred from the deploy command in AGENTS.md, not checked; the manual run E13 shows it). `deltalake` logs in through the Azure CLI with `storage_options={"azure_use_azure_cli": "true", "azure_tenant_id": <AZURE_TENANT_ID>}` (delta-rs docs via Context7). The same functions write to a local folder when given a local path and no storage options; unit tests use that.
- Registration: `client.statement_execution.execute_statement(statement=..., warehouse_id=..., wait_timeout=...)` returns a status (`PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, ...); `get_statement(statement_id)` polls it (v1 `routing-service/tpcds_api.py` `_execute_sql` shows the pattern). Databricks reads the columns from the Delta log, so `CREATE TABLE` has no column list. `client.tables.get(full_name)` raises `NotFound` for a missing table and returns its `comment`. Not verified: that a statement sent to a stopped warehouse starts it (expected; E13 shows it).
- The 24 tables (DuckDB's `tpcds` extension; `dbgen_version` excluded): `call_center`, `catalog_page`, `catalog_returns`, `catalog_sales`, `customer`, `customer_address`, `customer_demographics`, `date_dim`, `household_demographics`, `income_band`, `inventory`, `item`, `promotion`, `reason`, `ship_mode`, `store`, `store_returns`, `store_sales`, `time_dim`, `warehouse`, `web_page`, `web_returns`, `web_sales`, `web_site`. Not verified: that DuckDB's `dsdgen` creates exactly these; E5 checks it.
- Found in the E13 run (2026-11-14): "Write" worked (24 tables); "Register" failed at the first table with `PERMISSION_DENIED: Request for user delegation key is not authorized`, so nothing was registered. Verified in `infra/modules/storage.bicep`: the Unity Catalog identity has Storage Blob Data Contributor on the `tpcds` container only. Verified in the Databricks docs on Azure managed identities (Microsoft Learn, 2026-11-09): container-only access also needs Storage Blob Delegator on the storage account. Verified in the Azure built-in roles reference: Storage Blob Delegator is `db58b8e5-c6ad-4a2a-8342-4190687cbf4a`, whose only action is `Microsoft.Storage/storageAccounts/blobServices/generateUserDelegationKey/action` (no data access). Inferred, not verified: this missing role is the only cause; E13 shows it.
- Invariants:
  - Public repo: nothing committed may identify the company (AGENTS.md). The warehouse id is a company identifier: `.env` only, leak-checked.
  - Never managed tables: every table is external, at `abfss://tpcds@<DQR_STORAGE_ACCOUNT>.dfs.core.windows.net/<schema>/<table>/` (AGENTS.md).
  - The dev tool's existing guards stay as they are (AGENTS.md "Dev tool safety"). New code only targets the configured catalog, the fixed schema `sf1` and the 24 fixed table names.
  - Unit tests never call Azure or Databricks.
- Easy to get wrong:
  - Column types: Databricks must be able to read what `deltalake` writes. DuckDB can hand Arrow types that Delta has no name for (for example string views). E5 checks that every column of the written tables is one of `integer`, `long`, `decimal(p,s)`, `string`, `date`.
  - Memory: SF1 fits in memory, but pass each table to `deltalake` as a stream of record batches rather than one Arrow table, so SF10 later does not need a rewrite.
  - `INSTALL tpcds` downloads the DuckDB extension once; the E5 test needs network the first time on a machine.
  - Never print `.env` values in errors (the warehouse id included); name the variable.

## Decisions

| Decision | Options | Chosen | Why |
|----------|---------|--------|-----|
| Where SF1 is generated | Author's machine; a Container Apps job | Author's machine, DuckDB in memory | SF1 is about 1 GB; no new resource. Planner's call. |
| Tables | 24 data tables; plus `dbgen_version` | The 24 data tables listed in Context | `dbgen_version` is generator metadata, unused by the queries. Planner's call. |
| Scale factor | SF1 only; parameter | Functions take the scale factor and schema name; the menu offers SF1 → `sf1` only | SF10 reuses the code later. Planner's call. |
| Registration path | SQL on a warehouse; REST `tables.create` | SQL `CREATE TABLE ... USING DELTA ... LOCATION` through the Statement Execution API | Author's choice 2026-11-14: Databricks reads the schema from the Delta log, no hand-built column specs, no extra privileges; matches DESIGN §5. Costs warehouse minutes. |
| Which warehouse | Existing one, id in `.env`; one the tool creates and deletes | An existing warehouse, id in the new setting `DATABRICKS_WAREHOUSE_ID`; the tool only sends statements, never starts, stops or changes it | Author's choice 2026-11-14: least code; its own auto-stop shuts it down. |
| Money confirmation | None; yes/no | "Register" asks a yes/no question (default No) saying it uses the SQL warehouse, which costs money | DESIGN §2: Databricks calls that cost money need the author's explicit go. Planner's call. |
| Existing Delta data in a table folder | Skip; stop; overwrite | Skip the table and report "exists"; no overwrite, no delete action | Author's choice 2026-11-14: reruns write only what is missing; DESIGN §5 "written once". To rewrite, the author deletes the folder by hand. |
| File layout | One folder per table | `<root>/<schema>/<table>/`, root `abfss://tpcds@<DQR_STORAGE_ACCOUNT>.dfs.core.windows.net/` | Under our external location. Planner's call. |
| Existing table in Unity Catalog | Adopt; stop | Same rule as setup: with the marker comment it is "exists"; without it, registration stops before any statement | Never take over someone else's object. Planner's call. |
| Menu actions | One; write and register separately | Two new choices: "Write TPC-DS SF1 data" and "Register TPC-DS SF1 tables" | Only registration costs warehouse time; each can be rerun alone. Planner's call. |
| Row-count check | None; Databricks `count(*)`; Delta log | After each write, the row count recorded in the Delta log must equal the source's count; a Databricks count is the author's manual check | Free; catches a truncated write. Planner's call. |
| Settings per action | One loader for all; per action | Each action checks only what it needs: write needs `DQR_STORAGE_ACCOUNT`, `AZURE_TENANT_ID`; register needs `DQR_STORAGE_ACCOUNT`, `DATABRICKS_WAREHOUSE_ID` (catalog from `DQR_CATALOG` as today) | Writing must not need Databricks settings. Planner's call. |
| New dependencies | Runtime; separate group | `duckdb`, `deltalake` (and `pyarrow` if the Arrow hand-over needs it) as project dependencies | Same as the previous spec; image slimming is milestone 1. Planner's call. |
| Unity Catalog identity's access to our storage | Storage Blob Data Contributor on the whole account; Delegator on the account plus Data Contributor on the container | Add Storage Blob Delegator on our storage account; keep Data Contributor on the `tpcds` container only | Author's choice 2026-11-14 (option 1: fix inside this spec). The Delegator role gives no data access, so data access stays limited to the container. Our own storage account in `rg-dqr`; nothing in the dev resource group changes. Needs a DESIGN decision-log line. |
| Code layout | One module; per step | `src/dqr/data/tpcds.py` (table list, DuckDB source, `write_tables`, `register_tables`); menu in `src/dqr/cli/main.py` | DESIGN §9. Planner's call. |

## Examples
E1–E11 are unit tests: writing goes to a local temporary folder, Databricks is a fake client. E12 extends the leak guard. E14 is an offline Bicep check in `tests/test_infra.py`. E13 is the author's manual run.

- E1 — write to an empty root
  - Given: an empty local folder as root, and a fake source that yields the 24 table names, each with a small Arrow table (at least one row)
  - When: `write_tables` runs for schema `sf1`
  - Then: each table is a Delta table at `<root>/sf1/<table>/` with the same column names and rows as its source; the report has 24 lines in the order of the list in Context, each with status "written" and the row count.
- E2 — writing again changes nothing
  - Given: the state after E1
  - When: `write_tables` runs again with the same source
  - Then: no table gets a new Delta version (all stay at version 0), and the report shows 24 "exists".
- E3 — a partly written root
  - Given: only `<root>/sf1/store_sales/` holds a Delta table
  - When: `write_tables` runs
  - Then: `store_sales` is reported "exists" and stays at version 0; the other 23 are "written".
- E4 — row-count mismatch
  - Given: the Delta log of a table just written reports a row count different from the source's (faked in the test)
  - When: `write_tables` runs
  - Then: it raises an error naming that table and both counts, and writes no further table.
- E5 — the DuckDB source
  - Given: the real DuckDB source at scale factor 0.01
  - When: its tables are written with `write_tables` to a local folder
  - Then: the table names are exactly the 24 of Context (no `dbgen_version`), `store_sales` has at least one row, and every column in every written Delta schema has one of the types `integer`, `long`, `decimal(p,s)`, `string`, `date`.
- E6 — register into an empty schema
  - Given: a fake client where `dqr.sf1` holds no tables and every statement ends `SUCCEEDED`; `DQR_STORAGE_ACCOUNT=acct`, `DATABRICKS_WAREHOUSE_ID=wh`
  - When: `register_tables` runs for schema `sf1`
  - Then: it sends 24 statements to warehouse `wh`, in the order of the list in Context, each exactly ``CREATE TABLE `dqr`.`sf1`.`<table>` USING DELTA COMMENT '<MARKER>' LOCATION 'abfss://tpcds@acct.dfs.core.windows.net/sf1/<table>/'``; the report has 24 "registered" lines with the full table names.
- E7 — register again changes nothing
  - Given: all 24 tables exist with the marker comment
  - When: `register_tables` runs
  - Then: no statement is sent, and the report shows 24 "exists".
- E8 — an unmarked table stops registration
  - Given: `dqr.sf1.item` exists without the marker comment, the others do not exist
  - When: `register_tables` runs
  - Then: it raises an error naming `dqr.sf1.item`, and no statement is sent at all (all lookups run before the first statement).
- E9 — statement states
  - Given: (a) a statement that is first `PENDING`, then `RUNNING`, then `SUCCEEDED`; (b) the statement for `customer` ends `FAILED` with a message
  - When: `register_tables` runs
  - Then: (a) the table is reported "registered" after polling; (b) it raises an error naming `dqr.sf1.customer` and Databricks' message, and sends no statement for the tables after it. A rerun then reports the earlier tables as "exists".
- E10 — missing settings
  - Given: for write, `DQR_STORAGE_ACCOUNT` or `AZURE_TENANT_ID` unset or empty; for register, `DQR_STORAGE_ACCOUNT` or `DATABRICKS_WAREHOUSE_ID` unset or empty
  - When: that action's settings are loaded
  - Then: an error lists the missing variable names, never a value, before any DuckDB, Azure or Databricks call.
- E11 — menu
  - Given: faked prompts, as in `tests/test_cli.py`
  - When: the author picks "Write TPC-DS SF1 data", or "Register TPC-DS SF1 tables" and answers the yes/no question
  - Then: write calls `write_tables` for `sf1` with no confirmation; register asks the yes/no question first, calls `register_tables` only on yes, and calls nothing (not even the client factory) on no or cancel. Errors of both actions are shown as one message. The existing set up, tear down and quit choices behave as before.
- E12 — leak guard and settings template
  - Given: `.env` sets `DATABRICKS_WAREHOUSE_ID`
  - When: the leak-guard tests in `tests/test_infra.py` run
  - Then: no tracked or new file contains its value, and `.env.example` lists `DATABRICKS_WAREHOUSE_ID=` with an empty value and a one-line comment.
- E13 — real run (manual, plain result)
  - Done 2026-11-14: "Write TPC-DS SF1 data" wrote 24 tables (`store_sales` 2880404 rows).
  - Still to do, after E14 is deployed (what-if, then create) and the new role has had a few minutes to take effect: the author runs "Register TPC-DS SF1 tables" in the dev workspace. Its report shows 24 lines without error, and `SELECT count(*) FROM dqr.sf1.store_sales` in the Databricks SQL editor returns 2880404.
- E14 — Unity Catalog identity can get a user delegation key
  - Given: `infra/main.bicep` compiled offline, as the other tests in `tests/test_infra.py` do
  - When: the role assignments are inspected
  - Then: exactly one assignment has the Storage Blob Delegator role (`db58b8e5-c6ad-4a2a-8342-4190687cbf4a`). Its principal is the Unity Catalog identity's `principalId` (read from `ucIdentityResourceId`), with `principalType` `ServicePrincipal`. Its scope is the storage account, not a container. The existing E3, E4 and E7 infra tests still pass unchanged: the Unity Catalog identity still has exactly one Storage Blob Data Contributor assignment, on the container; the apps identity still has only AcrPull and Key Vault Secrets User; the writer role is still on the container.
