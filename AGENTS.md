# Project Instructions

This project follows the standard `ud:` command workflow. Run `/ud:next` to start.

## Tool Rules
- **NEVER use Glob to find files in dotfile directories** (`.taskmaster/`, `.agents/`, `.claude/`, etc.). Glob silently skips dotfile-prefixed paths. Use `ls` via Bash or `Read` on the directory instead.
- When a tool returns "no files found" for a path that should exist, **cross-check with a different tool** before concluding the files don't exist.

- **TLS interception side effects (PARTIALLY OUTDATED — verified 2026-06-07)**: This note previously claimed a network appliance breaks any C/C++ library validating TLS certs against `*.blob.core.windows.net`. **Hands-on testing on 2026-06-07 found NO TLS interception on the current network** — `openssl`/`curl` show the genuine DigiCert-signed Databricks cert with a clean chain, and DuckDB's `httpfs` reaches Azure/Databricks fine. The interception may have been present on a prior network but does not apply now. **Do not assume TLS interception when diagnosing C/C++ TLS failures — verify first with `openssl s_client -connect <host>:443`.** The credential-vending design (Python `urllib` for UC REST API calls + DuckDB `httpfs` for data files) remains correct and is retained, but the *reason* is no longer TLS interception — it's that DuckDB's native `unity_catalog` extension has a separate, confirmed bug: it sends a malformed body to `POST /temporary-table-credentials` and gets HTTP 400 for MANAGED Delta tables (upstream `duckdb/unity_catalog` issue #68). See the resolved "DuckDB native Unity Catalog extension" Ongoing Topic in PROJECT.md for the full investigation, the working extension recipe (unnamed secret + `LOAD azure`), and the decision to keep `credential_vending.py` until the upstream bug is fixed
- **Minikube image refresh**: The `latest` tag gets cached. To force an update: first `minikube ssh "docker rmi -f <image>:latest"`, then `minikube image load <image>:latest --overwrite=true`, then `kubectl rollout restart deployment/<name>`. Without the `docker rmi -f` step, `minikube image load` may silently keep the old tag. Verify with `minikube ssh "docker images <image>:latest --format '{{.ID}} {{.CreatedAt}}'"` after loading
- **DB schema management**: `routing-service/db/schema.sql` is the source of truth for fresh deployments, applied via a K8s Job + ConfigMap. Migration scripts in `db/migrations/` are kept for documentation but not run — at this stage, drop and recreate from `schema.sql`. To update schema: recreate ConfigMap (`kubectl create configmap postgresql-schema --from-file=schema.sql=routing-service/db/schema.sql --dry-run=client -o yaml | kubectl apply -f -`), delete old Job (`kubectl delete job postgresql-schema-init --ignore-not-found`), reapply Job (`kubectl apply -f k8s/postgresql-schema-job.yaml`). Tables use `CREATE TABLE IF NOT EXISTS` and seeds use `ON CONFLICT DO NOTHING` so the schema is idempotent. **Gotcha**: `CREATE TABLE IF NOT EXISTS` does NOT add new columns to existing tables — if a column is added to schema.sql, existing tables must be dropped first (`DROP TABLE ... CASCADE` in psql) before `make schema-update` will pick up the change. **Helm sync**: after modifying `routing-service/db/schema.sql`, always copy it to `infrastructure/helm/delta-router/files/schema.sql` — the Helm chart embeds it via `.Files.Get`
- **routing-service startup side effects**: Starting or restarting routing-service is not read-only. On startup it deletes `benchmark_runs` left in running/warming_up/pending status (results and warmups go with them via `ON DELETE CASCADE`), runs `query_features.backfill_all()`, and, if `DATABRICKS_HOST`/`DATABRICKS_TOKEN` are set, deletes `delta-router-ephemeral-*` warehouses carrying the management tag. Background threads then poll engine state every 30 s, scale idle on-demand DuckDB engines to 0, and hourly delete old `query_logs`/`routing_decisions` (retention from `log_settings`, default 30 days / 1024 MB). Before exporting or inspecting measured data, export first or scale routing-service to 0 right after the cluster starts
- **PostgreSQL credentials**: User is `delta`, database is `deltarouter` (no underscores). Secret in `k8s/postgresql-secret.yaml`. To get a psql shell: `make psql` or `kubectl exec -it postgresql-0 -- psql -U delta -d deltarouter`
- **db.py module**: `routing-service/db.py` provides a `ThreadedConnectionPool` (min 2, max 10) with `init_db()`/`close_db()` lifecycle, `get_conn()` context manager (auto-commit/rollback), and `execute()`/`fetch_one()`/`fetch_all()` helpers using `RealDictCursor`. Wired into FastAPI startup/shutdown events in `main.py`. All new database code should use this module instead of inline `psycopg2` connections
- **query_analyzer.py module**: `routing-service/query_analyzer.py` parses SQL via sqlglot, extracts table references (including three-part Unity Catalog names), counts features (joins, aggregations, subqueries, window functions), and computes a weighted complexity score. Returns a `QueryAnalysis` dataclass with an `error: str | None` field for parse-level problems (`"empty SQL"`, `"parse error"`; `None` means success). The analyzer is a pure data-extraction function — policy enforcement (e.g., rejecting non-SELECT) belongs in the routing layer
- **query_features.py module**: `routing-service/query_features.py` pre-computes and stores AST query features for ML training. Public API: `compute_and_store(query_id, sql)` (parses SQL via `query_analyzer`, inserts 10 AST features into `query_features` table), `compute_and_store_batch(rows)` (batch version for TPC-DS 99-query inserts), `update_table_metadata(query_ids, table_metadata)` (snapshots `total_data_bytes`/`max_table_size_bytes` at benchmark time), `backfill_all()` (fills missing rows on startup). Wired into: `collections_api.add_query()`, `tpcds_api._create_tpcds_collection()`, `benchmarks_api._run_benchmark_inner()`, and `main.py` startup. The `query_features` table is keyed on `query_id` (not `run_id`) since AST features are engine-independent
- **catalog_service.py module**: `routing-service/catalog_service.py` fetches table metadata from Unity Catalog via `databricks-sdk` with PostgreSQL-backed caching. Defines `TableMetadata` dataclass (full_name, table_type, data_source_format, storage_location, size_bytes, has_rls, has_column_masking, external_engine_read_support, cached). Public API: `get_table_metadata(full_name, workspace_client)` (cache-first, SDK fallback, UNKNOWN on error), `get_tables_metadata(table_names, workspace_client)` (batch dict). Cache uses `table_metadata_cache` PostgreSQL table with 5-min uniform TTL. SDK call: `workspace_client.tables.get(full_name, include_manifest_capabilities=True)`. Key field mappings: `table_type`/`data_source_format` are enums (`.value`), `row_filter is not None` → has_rls, `any(col.mask is not None for col in columns)` → has_column_masking, `"HAS_DIRECT_EXTERNAL_ENGINE_READ_SUPPORT" in securable_kind_manifest.capabilities` → external_engine_read_support, `properties["spark.sql.statistics.totalSize"]` → size_bytes
- **Metadata caching strategy**: "warm on browse, lazy on query" (documented in PROJECT.md). No background refresh job. When Task 9's tables endpoint lists tables via `tables.list()`, it caches metadata for all returned tables at no extra API cost. At query time, `get_table_metadata()` checks cache first. If cold-cache latency becomes an issue, first mitigation is parallelizing `get_tables_metadata()` with ThreadPoolExecutor
- **SELECT-only scope**: The router only supports SELECT statements. Non-SELECT SQL (INSERT, DROP, CREATE, etc.) must be rejected at the routing layer as a security boundary. The analyzer detects `statement_type` but does not enforce policy — update PROJECT.md when this is fully implemented

- **Databricks credential storage**: In-memory module-level state (`_workspace_client`, `_databricks_host`, `_databricks_username`, `_warehouse_id`, `_databricks_token`) in `routing-service/main.py`. Persisted to K8s Secret `databricks-credentials` via kubernetes Python client. K8s imports are inside `_save_to_k8s_secret()` (not top-level) so the module loads without errors in local dev outside a cluster
- **credential_vending.py module**: `duckdb-worker/credential_vending.py` implements the hybrid Python+DuckDB approach for reading Delta tables from Unity Catalog. Flow: UC REST API calls (Python `urllib`) → SAS token retrieval → `deltalake` library parses Delta log → ABFSS URIs converted to signed HTTPS URLs → SQL rewritten with `read_parquet()` → DuckDB executes via `httpfs`. Public API: `resolve_tables(tables, databricks_host, databricks_token)` returns `ResolvedTable` objects with parquet URLs. Key deps: `deltalake>=1.5.0` (v2Checkpoint/deletionVectors support), `pyarrow>=19.0.0`. Deletion vector filtering is NOT yet implemented — tables with active DVs may return deleted rows
- **DuckDB worker architecture**: `duckdb-worker/main.py` receives tables + Databricks credentials from routing-service per-request. Does NOT load the `delta` DuckDB extension — uses `httpfs` only. SQL is rewritten: three-part table names (e.g., `catalog.schema.table`) are replaced with `read_parquet(['url1', 'url2', ...])` calls. Routing-service passes `_databricks_host`, `_databricks_token`, and `analysis.tables` in the POST body to `/query`
- **Web-ui proxy pattern**: `web-ui/server.py` uses a single catch-all route `@app.api_route("/api/{path:path}")` that forwards all `/api/*` requests to routing-service. Health endpoints (`/api/health`, `/api/health/services`) are defined above the catch-all so FastAPI matches them first (handled locally). The catch-all forwards auth and content-type headers, query params, and request body. Returns 502 with `{"detail": "routing-service unavailable"}` on `httpx.ConnectError`. Static files mounted below via `StaticFiles`
- **Frontend auth flow**: Client-side auth via `AuthContext` + `ApiClient`. Login page (`src/components/LoginPage.tsx`) collects username/password, calls `POST /api/auth/login` through the proxy, stores opaque hex token in `sessionStorage("auth_token")`. `ApiClient` (`src/lib/api.ts`) attaches `Authorization: Bearer <token>` to all requests. On 401: clears token, fires `auth:unauthorized` custom event, `AuthContext` reacts by showing login page. `AuthProvider` wraps the entire app in `App.tsx`, outside `AppProvider`. TopBar shows username and "Sign out" button. Token uses `sessionStorage` (clears on tab close). No token refresh/expiry — backend tokens are in-memory and lost on restart
- **Cold start measurement protocol**: DuckDB engines always return 0ms (always-on, no startup cost — credential vending latency is per-request and already captured in ML predictions). Databricks engines: create ephemeral warehouse → wait RUNNING → stop → wait STOPPED → send `SELECT 1 FROM <table> LIMIT 1` to stopped warehouse → measure wall-clock time (warehouse auto-starts). Both standalone re-measure and benchmark warmup use this same protocol. The `benchmark_engine_warmups` table stores the raw warmup time for display; the `engine_cold_starts` table stores the routing-relevant value (0ms for DuckDB)
- **Scoring normalization**: `_normalize()` in `routing_engine.py` uses **ratio-based** normalization (`value / max`), not min-max. This preserves magnitude differences — a 10× slower engine gets a proportionally worse score instead of collapsing to {0, 1} for two engines
- **ML model engine matching**: `model_inference.predict_for_engines()` filters to the **intersection** of active engines and the model's `linked_engines`. It does not reject the entire prediction if some active engines aren't covered by the model
- **Logger naming**: Python loggers in routing-service modules must use the `routing-service.*` prefix (e.g., `logging.getLogger("routing-service.cold_start")`) to propagate to uvicorn's output. Using `__name__` produces a standalone logger with no handlers
- **Pre-existing test failures**: `tests/test_benchmarks.py` has ~38 pre-existing failures unrelated to current work. The passing tests (TestWarmupDatabricks, TestWarmupDuckDB, etc.) should be verified but the bulk failures should not block progress
- **Routing decision display**: `routingEventParser.ts` handles two scoring paths — ML scoring (events with `predicted=`, `norm_lat=`, etc.) and heuristic scoring (events with `fit=`, `cost=`, `total=`). The `RoutingDecisionView` table must handle both: ML path has full prediction/cold-start/tier data; heuristic path only has normalized fit/cost/total scores
- **Databricks execute_statement async pattern**: For long-running queries (warehouse startup from stopped can take 30-120s), use `wait_timeout="0s"` to get async mode, then poll `get_statement(statement_id)` until terminal state. The sync `wait_timeout` has a 50s ceiling

It is read in nearly every session, so keep it lean — no duplicated or stale content. Derivative documents (specs, prompts for external tools) should be generated from PROJECT.md, not maintained as parallel sources of truth

## Taskmaster Setup
This project uses Taskmaster MCP in **core-only mode** (no API key).
AI-powered Taskmaster features are handled by custom skills instead:
- `/ud:parse-prd` — parses PRDs into tasks (uses `parse-prd` skill, NOT the Taskmaster MCP `parse_prd` tool)
- `/ud:expand-task` — expands tasks into subtasks (uses `expand-task` skill, NOT the Taskmaster MCP `expand_task` tool)
- `/ud:new-prd` — generates PRDs from PROJECT.md (uses `generate-prd` skill)

Taskmaster core tools (get_tasks, next_task, set_task_status, etc.) work normally.

## Completing a Task
1. Check for deviations — if implementation diverged from the task, explain why and update the task details directly in `.taskmaster/tasks/tasks.json`
2. Mark done — use the `set_task_status` tool with status `done`
3. Summarize — run `/ud:summarize` (or write a `##### Task <id>: <title>` + 2-3 sentence summary)
4. Commit — ask before committing. Conventional commits: `feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`. Ask before pushing.

## Testing
- Every new module with logic (not glue/config) must include tests before the task is marked done.
- Tests live in `<service>/tests/` (e.g., `routing-service/tests/test_<module>.py`).
- Run with: `cd <service> && .venv/bin/python -m pytest tests/ -v`
- Pure functions and data-in/data-out modules are the priority — no need to mock databases for unit tests.
- Test categories: edge cases first, then feature correctness, then known-value regression (pin formulas/calculations).
